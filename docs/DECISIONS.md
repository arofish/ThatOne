# 架构审查与决策

初始审查：2026-10-14；2026-10-15 已有单层扫描实现与临时检查证据，M0 尚未通过。

## 关键风险

| 风险 | 当前处理 |
| --- | --- |
| 长期停留在文件管理，AI 迟迟无法验证 | M1 保持小范围，随后先做中文图文检索实验，再接最小原生界面 |
| 将目录名称当成真实元数据，影响搜索可信度 | 保存原始路径；日期只记候选与来源，不覆盖未来 EXIF 或人工信息 |
| 以路径或文件名当成永久身份，误合并版本 | Asset 用独立 ID；当前路径只用于扫描去重；移动识别和 Photo 关联延期 |
| 把扩展名识别当作有效图片验证 | M0 明确返回候选；解码、损坏文件处理在后续图像流水线中验收 |
| 文件系统会变化，外盘离线被误判为照片删除 | 扫描失败明确暴露；M1 不删除未见记录，在线状态与同步另行设计 |
| 多条件查询的向量相似度高，却不满足地点或标签约束 | M2 先评测视觉语义；M4 再设计结构化过滤和重排序，保留条件来源 |
| 开发期本地 API 能跑，但交付缺少进程安全与运行时管理 | 接口开发阶段明确监听范围与访问方式；分发能力单独验收 |

## 现在决定

1. 非破坏性、本地优先；核心实现以用户学习为主。
2. M0 使用 Python 标准库，范围仅为文件发现。扩展名白名单、链接、隐藏文件、排序和错误行为见首个任务。
3. M1 采用 SQLite、Asset 级索引；推断信息与观察到的文件信息分开。
4. M0 采用严格错误策略：不能完整读取目录就抛出异常，不将部分结果伪装成完整扫描。此策略未来可演进为“结果 + 错误列表”。
5. 不建立空的多层工程骨架；随着功能出现再划分模块。
6. 最小工程结构采用 `photoindex/`、`tests/`、`docs/`，用 `pyproject.toml` 记录项目信息与直接依赖。M0 只用标准库和 unittest；虚拟环境用 venv。第三方依赖与锁定工具在首次实际引入库时决定。
7. 从本地 Git main 分支开始，小任务分批提交；暂不建立远程仓库、CI 或复杂分支流程。
8. 2026-10-15 复查确认：本机 Python 3.14 的 `Path.exists()`、`is_dir()`、`is_file()` 等布尔查询可能隐藏底层读取错误。M0 的严格错误路径应使用能暴露错误的元数据读取与遍历操作，不以布尔查询的 `False` 推断所有失败都是“不存在”或“非候选”。根与子项的元数据错误都纳入模拟测试；不改变决策 4 的策略。
9. 2026-10-15 按用户希望减少决策负担的要求，后续任务先给高层路线，再给可连续完成的一批任务与验收条件。本批默认 `Path.iterdir()` + 列表显式栈，先建立单层测试，再修错误传播、增加子目录遍历并补全验收；整批交付后统一审查。这是本批实现与学习路线，不改变模块化单体架构。

## 可以延期

- 模型、MLX/PyTorch、中文文本编码器与向量索引选型：到 M2 核实内存、模型效果、耗时和占用。
- FastAPI 协议、端口、进程启动和访问控制：到首次接口实现时决定，不能拖到对外分发之后。
- EXIF 解析库和 HEIC/RAW 解码：到需要图像读取时，按真实文件与失败样本选择。
- 文件哈希、移动识别、Photo 多版本关系、可配置语义规则：有具体需求与样本后设计。
- 外盘离线管理、增量同步、后台任务：M5；Apple Photos：M6。
- App 内 Python 运行时、签名、公证：工程化阶段。

## 当前信息缺口

MacBook Air M4 来自用户说明，内存与开发环境尚未核实，不阻碍扫描器设计。真实目录命名样本在扩展 M1 语义解析前收集；不需要现在提供私人照片或完整路径。
