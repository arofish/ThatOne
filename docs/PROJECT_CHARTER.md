# PhotoIndex 项目章程

## 目标与协作

以 AI 为核心的 macOS 原生摄影作品管理与检索应用，同时作为用户学习 Python、后端、检索和 AI 工程的长期实践项目。

默认流程：需求 → 必要概念 → 方案设计 → 用户实现 → Code Review → 测试 → 验收。核心业务、算法、SQL 与 AI 流水线由用户先尝试实现；助手可处理文档、配置和重复工作。未运行、未验证的功能不能标记完成。

## 产品与安全原则

- 功能顺序：语义检索 → 素材管理 → 摄影 Agent → 风格分析。
- 数据源顺序：本地文件夹 → 外置硬盘 → Apple Photos。前两者共用文件系统逻辑。
- 默认不修改、移动、删除或强制复制原始照片。数据库、缩略图、Embedding 与原片分开保存。
- 云端 AI 默认关闭。外发照片或敏感信息前，明确数据内容、接收服务并取得用户授权。
- 日期、地点和工作流标签可能来自目录推断，应记录来源；不能自动等同于事实。工作流标签允许并存，不设计成固定状态机。
- Asset 是实际文件；Photo 是逻辑作品。先实现 Asset，不按文件名自动合并版本。
- Intent Search 结合路径、EXIF 与视觉检索；单个模型的结果不等于所有条件都已满足。
- 用户反馈和智能选片在可评测的检索基础上发展，Agent 在可靠工具基础上发展。

## 架构方向

采用模块化单体。SwiftUI 负责原生界面，Python 负责目录、元数据、检索、AI 和存储。SQLite 为初期持久化候选，NumPy 为初期精确向量检索候选；FastAPI 用于后续本地接口实践。

这些是方向，并非均已通过实验确认。M0 不引入 Web 服务或模型；模型选择在核实硬件、测试中文查询效果与性能后决定。开发期前后端可分别运行；可分发 App 的运行时、进程安全、签名和公证需要单独验收。

不提前引入微服务、复杂队列、专用向量数据库、大型 Agent 框架或复杂 RAW 解码。

## 最小里程碑

### M0：只读文件扫描器

输入本地目录，递归发现扩展名为 `.jpg`、`.jpeg`、`.png` 的普通文件，返回确定性排序的绝对路径列表。大小写不敏感，包含隐藏目录，跳过子树内的符号链接。无效根目录与读取错误必须明确暴露。

这是候选文件发现，不证明文件内容有效。不解析 EXIF、路径语义，不解码图片，不写数据库，不实现 CLI、UI、HTTP、AI 或缓存。用临时目录验证行为。

### M1：可重新扫描的本地 Asset 索引

在 M0 基础上，登记一个资料根目录并将 Asset 写入 SQLite。记录独立 Asset ID、资料源 ID、相对路径、扩展名、字节数和修改时间。以“资料源 + 相对路径”唯一约束避免重复记录；重复扫描更新现有行。文件信息读取失败需报告，不写入半条记录。

目录语义只做可解释的最小试验：保留相对目录路径，从明确的 `YYYY-MM-DD` 片段提取合法日期候选，记录原始片段和来源目录。候选可有多个；不自动选择拍摄日期。其他名称保留原文，不自动断言地点或标签。首版范围有限，不要求用户改名；后续按真实样本扩展规则。

首次交付只承诺新增与现有路径更新；不推断移动、版本关系，不删除本轮未见的旧记录，也不宣称旧记录均在线。完整缺失状态与增量索引归 M5。

验收：扫描嵌套样本后能查询已保存的 Asset；重启后数据仍在；重复扫描不增加重复行；文件大小或修改时间变化能更新；合法与非法日期、多个日期候选有测试；所有原文件内容和位置保持不变。

## 后续交付节奏

M1 后尽快交付 M2 的小型图文检索实验，用真实中文查询建立小规模标注样本，再连接 M3 最小 SwiftUI 搜索界面。不要等完整元数据、RAW 或 Agent 做完才验证 AI。

M4：混合检索与反馈；M5：增量索引、恢复与性能；M6：外置 RAW 与 Photos；M7：Agent 与智能选片。范围随证据调整。
